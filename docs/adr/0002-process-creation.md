# ADR-002: создание процессов через `spawn`, а не `fork`

- **Статус:** Accepted
- **Дата:** 2026-11-14
- **Контекст релиза:** M1, после `v0.6.0`

## Контекст

Текущий загрузчик ELF64 загружает один статический образ в отдельное
адресное пространство и запускает его синхронно через `user::run`. Планировщик
и таблица процессов существуют, но полноценного copy-on-write, demand paging
и многопроцессного userland ещё нет.

В `kernel/src/proc/mod.rs` есть заготовка `fork()`, однако она клонирует
`Arc<AddressSpace>` и копирует таблицу файловых дескрипторов. Это не создаёт
независимого адресного пространства: запись в память ребёнка изменит память
родителя. Такая заготовка не должна попасть в ABI как рабочий `fork`.

Для M1 нужны как минимум запуск программы из bSH, ожидание завершения и
простой конвейер. Полный `fork` с COW для этого не обязателен.

## Решение

1. Основной примитив создания процесса — `spawn(path, argv, env, fd_map)`.
   Он загружает новый ELF64 в новое адресное пространство, создаёт процесс и
   возвращает `pid` родителю.
2. Для ожидания используется `wait(pid, status, flags)` с блокирующим
   режимом и `WNOHANG`. `wait(-1, ...)` ждёт любого ребёнка.
3. `spawn` наследует стандартные дескрипторы `0`, `1`, `2`; дополнительные
   дескрипторы передаются явной таблицей `fd_map` (родительский fd →
   дочерний fd). Неявное наследование всех открытых файлов запрещено.
4. Конвейеры строятся как `pipe()` + `spawn()` + `dup2()`; оболочка
   закрывает лишние концы pipe после запуска каждого процесса.
5. `fork()` не входит в ABI M1. Заготовка `proc::fork()` либо удаляется,
   либо возвращает `ENOSYS` до появления COW-клонирования страниц.
6. `exec()` остаётся операцией замены образа текущего процесса. В M1 он
   может использоваться внутри `spawn`, но не заменяет собой создание
   процесса.
7. `fork()` с COW рассматривается после M2, когда появятся:
   - refcount на физические страницы;
   - корректное клонирование таблиц страниц;
   - обработка `fork` в планировщике и `wait` для зомби;
   - тесты на изоляцию адресных пространств.

## Последствия

- Первый многопроцессный userland можно сделать без сложной COW-машины.
- bSH сможет запускать `.bh`, ждать код возврата и строить простые pipe.
- Программы, которым нужен именно `fork`, не заработают до M2/M3. Это
  осознанное ограничение, а не скрытая недоделка.
- Нужны новые системные вызовы и ABI-документ; номера фиксируются до
  реализации libbos.
- Тесты M1 должны проверять: независимость адресных пространств,
  наследование `fd_map`, закрытие pipe, `wait` и `WNOHANG`.

## Альтернативы

- **Сразу полноценный `fork` с COW.** Даёт совместимость с Unix-программами,
  но требует зрелого VM, refcount и отладки page faults. Для M1 это
  неоправданный риск.
- **`fork` без COW с полным копированием памяти.** Проще в реализации, но
  дорого и опасно для больших образов; к тому же текущая заготовка не делает
  даже этого.
- **Только `exec` без создания процессов.** Не позволяет запускать
  несколько программ и строить конвейеры.
